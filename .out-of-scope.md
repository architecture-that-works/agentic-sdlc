# Out of Scope

Concepts explicitly deferred or rejected — the single ledger (CONTEXT.md only links here). Each `## `
heading is a searchable entry for plan-phase deduplication; append new entries in the same shape.

---

## Embedded web framework (FastAPI/Flask) in the hello-world starter

**Date:** 2026-05-12
**Reason:** Standard Library First constraint; stdlib `http.server` is sufficient for the hello-world starter. Introducing FastAPI or Flask would pull in a third-party dependency that the template does not need and that forks would have to justify removing.
**Source ADR:** N/A — constraint originates from CONTEXT.md Architectural Constraints ("Standard library first").

---

## Multi-variant template (separate per-type scaffolds)

**Date:** 2026-05-10
**Reason:** Replaced by a single template with a `project_type` prompt; specialised directory stubs deferred until a concrete project demands them. Maintaining separate scaffolds per project type would multiply template surface area without proportionate benefit at the current maturity level.
**Source ADR:** N/A — recorded in CONTEXT.md §Out of Scope on 2026-05-10.

---

## Gemini as primary AI provider

**Date:** 2026-05-09
**Reason:** Claude-first architectural constraint (CONTEXT.md). Gemini stays an optional local engine for `task hitl`; headless Gemini was dropped from the cloud pipeline on 2026-09-20. Elevating it would require re-evaluating every skill prompt.
**Source ADR:** N/A — constraint originates from CONTEXT.md Architectural Constraints ("Claude-first AI").

## Separate CLAUDE.md for behavioural rules

**Date:** 2026-05-11
**Reason:** Rejected in ADR-009. `AGENTS.md` is the single standing-instructions file (cross-tool convention). A separate `CLAUDE.md` would split the source of truth and privilege one vendor over others.
**Source ADR:** [ADR-009](docs/adr/ADR-009-context-strategy.md) — Option A rejected; Option B chosen.

---

## Generic Module Map per project_type (separate maps for application / agent / ml)

**Date:** 2026-05-11
**Reason:** Rejected in ADR-009. A single Map at template-time lists only invariant rows; project_type-specific rows are added as the first feature lands. Separate per-type maps would fragment the navigation surface and increase maintenance overhead.
**Source ADR:** [ADR-009](docs/adr/ADR-009-context-strategy.md) — confirmation criterion: "Module Map at template-time is shallow by design".

## Codespace as HITL validation surface

**Date:** 2026-05-12
**Reason:** HITL surface is the developer's laptop indefinitely. Persistent Cloud Run Orchestrator Service is the Phase-3 cloud-runtime north star, not Codespaces. Codespaces adds provisioning latency and environment parity risk without advancing the current maturity target.
**Source ADR:** N/A — recorded in CONTEXT.md §Out of Scope on 2026-05-12.

## LangGraph (or any agent-framework library) as orchestrator runtime

**Date:** 2026-05-12
**Reason:** Drag too high for a template — forks should not need to learn LangGraph. Patterns (declarative graph, checkpoint, interrupt) are stolen without the dependency. Adding LangGraph would make the template non-trivial to fork and would contradict the "standard library first, minimal dependencies" ethos.
**Source ADR:** N/A — recorded in CONTEXT.md §Out of Scope on 2026-05-12.

## Persistent Cloud Run Orchestrator Service (Phase-3 north star)

**Date:** 2026-09-23
**Reason:** Deferred. The GitHub Actions pipeline (`afk.yml`) is the runtime; a persistent FastAPI-on-Cloud-Run service is only worth its operating cost once that pipeline runs unattended reliably. The original spike also assumed `state.json` and `.planning/`, both superseded by the issue-body carrier (ADR-011, ADR-014). Includes the gating sandbox-liability decision (own container vs remote sandboxes), which only matters once untrusted code runs outside GitHub Actions.
**Source:** [#88](https://github.com/ysuurme/my_template_repo/issues/88), [#161](https://github.com/ysuurme/my_template_repo/issues/161)

## Planner/Generator/Evaluator (PGE) agent split

**Date:** 2026-09-23
**Decision:** Dropped.
**Reason:** The review stage already provides a dedicated evaluation pass that runs after implementation, giving separation of generation from evaluation at the stage level. Adding a within-stage PGE split introduces coordination overhead and prompt-engineering complexity with no concrete failing scenario to fix. Nothing in `.github/orchestrator/` implements or depends on the pattern.
**Source:** [#212](https://github.com/ysuurme/my_template_repo/issues/212)

---

## `emitEvent` durable event log

**Date:** 2026-09-23
**Decision:** Dropped.
**Reason:** The issue body (AGENT-STATE block, `attempts[]`) is already the durable per-issue record mandated by ADR-011. A parallel `emitEvent` log would duplicate that state in a second medium, violating the single-carrier constraint. The orchestrator has no surface that calls `emitEvent`, and the existing signal-comment / noise-comment convention covers the observability need.
**Source:** [#212](https://github.com/ysuurme/my_template_repo/issues/212)

---

## Tool-call offloading rules

**Date:** 2026-09-23
**Decision:** Dropped.
**Reason:** The GitHub Actions runner model has no dynamic tool-call routing surface — every stage runs in the same ephemeral container via `Invoke-Orchestration`. Offloading rules presuppose a persistent process that can redirect individual tool calls at runtime; that infrastructure (the deferred Cloud Run service) is itself out of scope. Nothing in `.github/orchestrator/` implements or consumes offloading rules.
**Source:** [#212](https://github.com/ysuurme/my_template_repo/issues/212)

---

## Cline-style Plan/Act loop as alternative to the fixed refine→architect→plan gate

**Date:** 2026-09-25
**Reason:** The fixed gate is fully implemented and relied upon by ADR-014 and ADR-015; the six-stage conductor, agent:backlog grant, in-issue decisions, and auto-implementation on agent:backlog are all built on it. The Plan/Act read/write safety boundary only matters in long-lived interactive sessions — not the ephemeral GitHub Actions containers where this pipeline runs — so it offers no benefit here. Adopting the loop would require re-implementing the gate, in-issue decisions, and six-stage conductor with unbounded scope.
**Source ADR:** [ADR-014](docs/adr/ADR-014-pre-backlog-alignment-gate.md), [ADR-015](docs/adr/ADR-015-pipeline-taxonomy.md)

---

## Plan Adherence (and trajectory re-judging) as an eval

**Date:** 2026-09-25
**Decision:** Rejected.
**Reason:** The review stage already judges, on every pipeline PR, whether an implementation follows its issue's plan and acceptance criteria. An eval that re-judges plan-following would duplicate that agent with a second, differently-prompted judge. Evals judge *components* (a prompt, skill or LLM call) against fixed goldens; review judges *changes*. Criterion 5.6 is met with G-Eval, Answer Relevancy and Tool Correctness.
**Source:** [#155](https://github.com/ysuurme/my_template_repo/issues/155)
